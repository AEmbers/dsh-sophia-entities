# 多页面支持计划

本文件是方案与待定决策，不定义已实现行为。2026-09-17 核查。

## 1. 支持目标

推荐将每个 Web 页面视为独立的使用界面，而非竞争唯一控制权的终端。一个 Host 继续拥有 Team 事实和 Agent 运行；页面只负责自己的展示和操作请求。

| 场景 | 推荐目标 | 验证范围 |
| --- | --- | --- |
| 同一浏览器多个标签页 | 同时正常加载和操作，不要求关闭其他页面 | 第一阶段必须覆盖，共用 BrowserContext |
| 多个窗口并排可见 | 两个页面均可持续更新，不以焦点决定控制权 | 浏览器验证；focus 不等于 visibility |
| 同一 Host 的多个浏览器或设备 | 不引入单页限制，Host 状态保持一致 | 分离 BrowserContext 验证；不宣称覆盖所有设备与网络 |
| 后台隐藏页面 | 不干扰前台；冻结或断线后可恢复到 Host 最新状态 | 正确性必须覆盖，主动节流暂不实施 |
| 多个 Host 进程或多人账号协作 | 不在本次范围 | 现有 Human 身份与 Host 权限模型不改变 |

交互目标示意（不新增控件）：

```text
同一个 Host
  ├─ 窗口 A [频道 engineering]  可见，正常更新
  ├─ 窗口 B [成员列表]          可见，正常更新
  └─ 标签 C [Thread]            隐藏，不夺取 A/B 控制权
       再次打开 → 恢复所需订阅与最新数据
```

“支持多个页面”不代表无限页面零成本。第一阶段选择 1、2、4 页作为可重复回归样本，不设置人为的产品页数上限。

## 2. 传输方案取舍

| 方案 | 结果与代价 | 判断 |
| --- | --- | --- |
| 仅允许一个活跃页面连接 | 需要活跃页定义、接管和失效处理；不能自然支持并排窗口 | 不推荐 |
| 缩短长轮询或增大读取超时 | 同源 HTTP 连接竞争仍存在；分别增加请求频率或等待时间 | 不作为根本修复 |
| 每页使用现有 Remote WebSocket，scope 订阅共享该连接 | 利用 Harness 已有连接恢复；普通读取不再被 Team 长轮询占住 | 推荐第一阶段 |
| 多页通过 SharedWorker / BroadcastChannel 共用一个物理连接 | 增加跨页生命周期与消息路由；跨浏览器和设备仍不能共用 | 当前无必要，不实施 |
| 改部署为 HTTP/2 或停用开发事件连接 | 可能改变瓶颈出现的阈值，但不能作为 Team 的使用前提 | 不作为本次修复 |

复用是“一个页面内的多个逻辑订阅共用 Harness 已有 WebSocket”，不是所有页面共用一个连接。Team 不建立自己的连接管理器、重试调度器或第二份事实存储。

## 3. 第一阶段设计约束

### 订阅与读取

- 更新消息只表示对应 scope 的投影可能变化，事实仍由 Host 读取接口返回，不把 ledger 原始记录发给页面。
- 保留全局、Workspace、Channel、Thread、Presence 的范围区分；Presence 不触发频道内容或全局 Inbox 重读。
- 一个页面内同一 scope 的多个使用者共享一个逻辑订阅。改变传输不要求把组件改成直接理解 WebSocket 或连接代次。
- 每个订阅建立时必须有可识别的就绪/当前版本信息；恢复连接也必须能重新读取，即使版本数字没变。具体消息字段在实施前确定，不预先固定新 DTO。
- 首次读取与建立订阅之间不能漏掉变化。可采用先建立监听再读取，或收到就绪信息后执行一次可合并的补读；不能机械保留现有首次静默采样的竞态窗口。
- 每个 scope 的版本只在自己的域内比较。Host 重启导致 Presence 版本回退时重新建立基线，不把它当成旧消息丢弃。
- 通知允许合并到最新版本，因为消费者会重新读取；必须避免慢消费者期间形成无界事件队列。实际变更历史不通过本通知接口保证逐条送达。

### 生命周期与错误

- Harness 负责物理连接与恢复；Team 负责 scope 生命周期、恢复后的重新读取和向现有界面交付失败状态。
- 区分可恢复的传输中断与终止性的业务/协议错误，不能对已归档资源或权限错误无限重试。
- 最后一个使用者离开、退出 Team、卸载插件或关闭页面时，取消对应订阅并释放 Host 监听。取消一个页面不得取消其他页面。
- 已失效的订阅返回不能覆盖新页面状态；开关频道、订阅尚未就绪时关闭、断线中退出都要覆盖。
- 删除旧 HTTP 长轮询、25 秒等待路径和 Team 自有退避；不要保留静默回退。更新前已经打开的旧 Client 如何获得新 bundle 按 Harness 实际加载机制验证，不额外构建双协议兼容层。
- 草稿、Host 幂等键、revision 和授权保持原责任归属；通知重连不能自动重发用户的持久操作。

## 4. 多页面状态清单

以下是扩大支持承诺前必须检查的正确性事项，不是第一阶段已经修复的内容。

| 状态 | 已检查的当前实现 | 风险或问题 | 推荐下一步 |
| --- | --- | --- | --- |
| 实时订阅 | 每页独立长轮询，同页按 scope 去重 | 已复现连接竞争 | 任务 01 修复 |
| 导航与恢复 | 运行时各页独立，启动读取同一个 localStorage 快照，未监听跨页 storage 事件 | 已打开页面不会主动联动；重载可能恢复另一页最后保存的位置 | 验证后推荐每标签页恢复自己的位置；新页的默认入口另行明确 |
| 消息草稿 | 各页持有独立内存副本，写入时替换整个共享 localStorage 字典 | 可能覆盖另一页保存的草稿，连不同 Thread 的草稿也可能受影响 | 先用双实例/真实双页验证；推荐草稿按标签页隔离，不自动覆盖正在输入的内容；跨页共享草稿是另一种需明确选择的契约 |
| Inbox 和已读 | Host 读进度不唤醒共享 changes；成功读取只 bump 当前 Client 的 TeamReadStream | 另一页 Inbox 可能不随本页读取及时减少 | 验证同一 Human 的读进度传播；不为刷新 badge 唤醒所有公共内容订阅；仅浏览器广播不能覆盖分离浏览器 |
| 隐藏 Thread 的自动读取 | Thread 加载/刷新调用持久 readThread，所查路径没有 visibility 条件 | 隐藏页可能消耗用户尚未看到内容的未读状态；不能与后台节流混为一谈 | 验证来消息与隐藏/恢复组合；推荐只有可见阅读界面自动确认已读，并排可见窗口不要求焦点 |
| 同时编辑和发送 | Host 已有 revision、幂等与授权检查 | 冲突反馈、重复点击、过期页面行为需要多页验收；不允许 Client 乐观覆盖 Host | 保留现有 Host 规则，验证实际冲突可理解、失败保留输入 |
| 排序与折叠偏好 | 使用浏览器本地存储 | 是否跨页即时同步不影响加载修复；持久覆盖语义仍需检查 | 不为偏好新增通用同步框架，有实际损失再处理 |

这些路径有源码依据，但除连接阻塞外尚未在本工作项做定向行为复现。实施第一阶段时不顺带更改这些产品语义。对草稿、已读等真实正确性缺陷完成复现后，单独确认方案并建立纵向任务，不归为可有可无的性能优化。

## 5. 执行顺序

1. 用户授权后执行任务 01：将现有诊断升级为真实浏览器回归，同一纵向改动完成流式通知替换和恢复/取消验证。
2. 流式版本中复测页面数量、可见性、空闲与持续消息下的请求量；确认普通 DSH 页面和开发事件连接仍可用。
3. 对状态清单做定向验证，优先草稿丢失、自动已读和跨页读进度，再明确导航恢复契约。方案收敛后写 `spec.md`、建立后续任务，不用占位实现任务伪装已决定范围。
4. 仅当测量表明后台投影读取/渲染有实质负担，才设计隐藏页合并刷新：记录待刷新 scope，恢复时补读；具体是否保留逻辑订阅由生命周期测量决定。不得取消 Host Agent 工作，也不得引入“唯一主标签页”。

## 6. 验收矩阵

| 验证项 | 方法 | 通过条件 |
| --- | --- | --- |
| 同源连接阻塞 | 干净 Chrome，单 Host，同一 BrowserContext 的 1/2/4 页；页内发真实查询 | 固定小数据集的成员/频道查询在 3 秒内完成，无约 25 秒排队；3 秒是回归阈值，不是产品 SLA |
| 界面可用 | 频道、Thread、Inbox、成员和普通 Session 混合打开 | 真实 DOM 完成加载，切换/操作有响应，不能仅用 HTTP 200 判定 |
| 通知送达 | 一页提交内容，另一页观察；Presence 单独触发 | 所有相关页面看到 Host 最新状态，无无关 scope 重读风暴 |
| 初始与恢复竞态 | 控制首次读取/订阅就绪之间提交；断线期间提交 | 不漏变化；未发生新提交的重连也恢复失败的读取 |
| 生命周期 | 关闭一页、退出 Team、快速切换、连接断开期间取消 | 其他页面不受影响，Host 监听和队列不持续增长 |
| 可见性 | 并排窗口、主动隐藏/显示、睡眠或断线后恢复 | 不把失焦当独占权丢失；不宣称 headless bringToFront 已覆盖操作系统冻结 |
| 分离浏览器 | 两个 BrowserContext，共同连接同一 Host | 内容更新不依赖 localStorage/BroadcastChannel 互通 |
| 版本与部署 | 当前声明最低版本及实际开发 checkout；区分 HMR 持续连接 | 有真实构建运行证据，不以 rc.2 实测代替 rc.1 兼容验证 |
| 性能复测 | 记录普通请求耗时、通知与补读次数、空闲/活跃页的负担 | Team 不再以持续 HTTP 请求占用连接；残余瓶颈有数据后再立项 |

先运行改变面的 Host/Client 测试，再运行 typecheck/build 和 `npm run test:browser`。涉及可见交互变化时遵循仓库桌面、390×844、键盘/焦点及加载/错误/空态检查。日常日志和截图保持忽略，只有人工认可的里程碑材料进入 validation。
